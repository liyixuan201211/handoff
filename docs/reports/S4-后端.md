## 发现的问题 / 风险

### 🔴 R1（已报告 main，已在其侧修复）：engine 的可选依赖加载静默返回 null，数据只落内存

`src/pipeline/engine.js` 的 `optional()` 签名是 `(specifier, exportName)`，但四个调用点都不传
`exportName`，于是 `mod[undefined] ?? mod.default ?? null` 恒为 `null`。我的 store 只有具名导出
（契约要求），因此 `deps.saveJob` 永远是 null，engine **静默退回到它自己的内存 `fallbackSave`**。

后果：`POST /api/jobs` 返回 201，但紧接着 `GET /api/jobs/:id` 与 `/stream` 全是 404，data 目录
一个文件都没有 —— 刷新页面任务全丢。

我的实测证据：
```
$ HANDOFF_DATA_DIR=/tmp/handoff-dbg node -e "…await e.loadOptionalDeps(); console.log(typeof e.deps.saveJob)"
object null                      ← 应该是 function
$ ls /tmp/handoff-int2/jobs/
(空)
```
已通过消息给出两种一行修复方案。main 已在 `src/pipeline/engine.js` 修复并写了教训注释；
我复测确认：`POST` 后 `GET` 能读到，且磁盘上有文件。

**我自己的加固**：`POST /api/jobs` 里加了一层幂等兜底 —— 只要 job 已经返回给客户端，就保证
`saveJob` 过（`getJob` 命中就不重复写）。理由：持久化是「刷新页面还在」这个承诺的底座，
不该依赖调用方的实现细节。测试 `创建后立即可读（持久化兜底）` 覆盖。

### 🟠 R2（真实踩到，已修）：Express 5 里路由**之后**注册的中间件对该路由不会执行

我最初把限流写成 `app.use(limiter)` 挂在 `createApp()` 之后，结果 11 次请求全部 201，限流完全失效。
最小复现：
```
bare express 5: app.use('/api', router); app.use(mw) → mw 不执行（无日志）
                app.use(mw); app.use('/api', router) → mw 执行
```
修法：限流器必须在 `createApp()` 内部、挂路由**之前**注册。为此 `createApp` 增加了
`{ limiter }` 注入口（测试要控制时钟时用）。**这条对 S5/S6 也有用**：任何想在 API 前加中间件的人
都不能事后 `app.use`。

### 🟡 R3：SSE 连接原本要等 15 秒才吐第一个字节

刚创建、还没有任何事件的 job，`sseHandler` 只订阅不写，客户端要等到第一次心跳才收到字节
（我最初的断开测试因此超时 3s 才发现）。已加立即下发的 `: connected` 注释帧（不触发
`onmessage`，纯保活）。这直接影响前端「转圈圈卡住」的观感。

### 🟡 R4：`sent` Set 是稳定增长的内存泄漏

补发区间与实时推送可能重叠，我最初用 `Set` 去重，连接挂几小时就会累积。已改为单调游标
`lastSent`，O(1) 内存。

### 🟡 R5：main 的 `plan` 阶段会长时间挂住（未修，不在我职责内）

一次真模型跑，`plan` 阶段的一次 HTTP 调用开着超过 13 分钟仍未超时（`usage.calls=1`，
`ms=39908` 后 job 文件不再变化）。契约 §4 要求 `timeoutMs` 默认 120s。前端此时会一直显示
「项目经理 制定方案 运行中」。建议 main 检查 `callModel` 的 timeout/abort 是否真的作用到了
`fetch`（以及 `ctx.aborted` 是否能中断在飞的请求）。
