### 【真实缺陷 1】输入阶段的注入 finding 永远不会进入最终 `job.security`

**位置：** `src/pipeline/engine.js:919`

```js
return deps.guard.auditJob({ artifacts, review: job.review, plan: job.plan });
//                                            ↑ 少传了 security
```

**判断依据：** `auditJob` 的签名是
`export function auditJob({ artifacts = [], review = null, plan = null, security = null } = {})`（`src/security/guard.js:706`），
而它内部 `guard.js:709-710` 就是：

```js
// 0) 把输入阶段已经标记过的注入 finding 带进来（否则 job.security 会漏掉它）
if (security && Array.isArray(security.findings)) { ... }
```

`runSecurityAudit` **不传 `security`**，所以这段**永远是死代码**。后果：`startJob` 在输入阶段
确实把注入 finding 写进了 `job.security`（`engine.js:194`），但 `execute` 收尾时
`job.security = mergeSecurity(job.security, security)`——`mergeSecurity`（`engine.js:925-933`）在 `b.findings`
为空时保留 `a`，所以输入阶段的 finding **侥幸没丢**。

**那这个 bug 的实际危害是什么？** 它让 `auditJob` 的**去重与合并能力失效**：如果同一段注入内容
既出现在 goal 里（输入阶段记一条），又出现在产物里（输出审计记一条），两条 finding 的
`where` 不同（`goal` vs `artifact:xxx`），本应被 `auditJob` 的步骤 3 统一收敛；现在它们
在 `mergeSecurity` 里**无条件 concat**，用户会在界面上看到同一件事被报两遍。

**修法（一个词）：** `runSecurityAudit(job, artifacts)` 里补 `security: job.security`。

### 【真实缺陷 2】`validateDelivery` 的最后一段循环是死代码

**位置：** `src/pipeline/engine.js:962-974`

```js
const substantial = realArtifacts.filter(
  (a) => typeof a.content === 'string' && a.content.replace(/\s/g, '').length > 80,
);
if (realArtifacts.length && !substantial.length) {
  problems.push('产出的内容太少，没有实际价值');
}
// 只要有一份像样的东西，就算部分成功；全都不像样才是失败
for (const a of substantial) {
  if (a.content.replace(/\s/g, '').length <= 80) {   // ← 永远为 false
    problems.push(`「${a.name}」内容太短`);
  }
}
```

**判断依据：** `substantial` 的定义就是"去空白后长度 **> 80**"，循环里再判 "**<= 80**"——
同一个数组、同一个表达式，**矛盾条件，永远不成立**。这段代码一行都执行不到。

**它想做什么？** 看注释和 `problems` 的文案，作者想区分"全部太短"和"个别太短"。
但契约 §7 的门槛本来就是"至少一份达标即算交付成功"（注释也这么写了），所以这段
**不需要存在**——删掉即可。留着它比删掉更糟：读代码的人会以为"个别太短"也在被处理。

### 【真实缺陷 3】`MIN_ARTIFACT_LENGTH` 被导出却被硬编码绕过

**位置：** `src/security/guard.js:30`（定义）vs `src/pipeline/engine.js:963`（硬编码 80）

**判断依据：** 安全工程师在 `guard.js:163-164` 和报告里明确写了意图：

> 顺带我把 `MIN_ARTIFACT_LENGTH=80` 作为常量导出，**让 S3 的质量门禁和我的判断用同一个数**，
> 避免两边口径不一致。（`docs/reports/S6-安全.md`「我尝试攻击但没能成功的 3 个思路」③）

而 `engine.js` 的 `validateDelivery` 写的是字面量 `80`，**没有 import 这个常量**。
实测 `grep -rn "MIN_ARTIFACT_LENGTH" src/ tests/` 只有 3 处：定义 1 处、guard 自己用 1 处、
测试断言 1 处。**engine 一次都没引用。**

**危害：** 两处口径目前恰好相同（都是 80），纯属巧合。**改一边，另一边不会跟着变**，
而且是静默不一致——这正是导出这个常量要防的事。同理，两边"是否去空白"的口径也不同：
guard 数的是**全部产物去空白后的总和**（`nonWhitespaceLength`），engine 数的是**单个产物**。

### 【真实缺陷 4】`.env` 文件根本不会被加载（README 与 `.env.example` 都在骗人）

**位置：** `package.json`（无 `dotenv`）、`src/server.js:338-340`（只读 `process.env`）

**判断依据（实测，不是推理）：** 我往 `.env` 里写了 `HANDOFF_PORT=59999`，然后启动服务：

```
$ cat > .env <<'EOF'
HANDOFF_PORT=59999
HANDOFF_DEMO=1
EOF
$ node --input-type=module -e 'const {startServer}=await import("./src/server.js"); ...'
[server] 交接 Handoff 已启动：http://127.0.0.1:8787  (dataDir=/var/folders/.../tmp.OKv6YjYcC3)
实际监听: http://127.0.0.1:8787
.env 里写的是 HANDOFF_PORT=59999
```

**监听的是 8787，不是 59999。** 全仓确认：`node_modules` 里没有 `dotenv`，
`package.json` 的 scripts 里没有 `--env-file`，`src/` 里没有任何读取 `.env` 文件的代码。

**为什么这条严重：** `.env.example` 的标题是"交接 Handoff — 环境变量（全部可选！）"，
`README.md` 的常用配置一节说"在项目根目录建一个 `.env`（照 `.env.example` 抄）"，
`src/llm/gateway.js:111` 的报错文案甚至直接教用户"可以在项目根目录的 .env 里填"。
**三条对用户的承诺，一条都不成立。** 而目标用户正是"不会配环境变量"的普通人——
他们会照做，然后发现"我明明设了端口，它还是开在 8787"。

顺带：`HANDOFF_DATA_DIR`、`HANDOFF_DEMO`、`HANDOFF_LLM_TIMEOUT_MS` 写在 `.env` 里**同样无效**。

**修法（二选一）：** ① `npm start` 改成 `node --env-file=.env src/server.js`（Node 22.5+ 原生支持，
不违反零依赖）；② 从 README 和 `.env.example` 里删掉 `.env` 的说法，改成教用户
`HANDOFF_PORT=59999 npm start`。

**额外发现：** `.env.example` 里的 `AIPING_BASE_URL` **没有任何代码读它**
（`grep -rn "BASE_URL" src/` 里只有 `providers.js` 的硬编码常量）。硬编码本身是防 SSRF 的
正确设计，但 `.env.example` 列它会让人以为可以改。

### 【真实缺陷 5】前端错误码映射表覆盖了不存在的码，漏掉了最常见的码

**位置：** `public/api.js:24-33`（映射表）vs `src/llm/gateway.js:412`（真实抛出的码）

走到兜底分支 `if (msg && !/^[A-Z_]+$/.test(msg)) return msg;`——而 message 是一句中文

**测试还把这个错误固化了**：`tests/unit/frontend.test.js:443-444` 断言
`friendlyError({code:'JOB_NOT_FOUND'})` 要包含"找不到了"——**后端永远不会产生这个码**，

### 【我怀疑但**验证后不成立**的**（记录一下，省得下一个人再查一遍）

诚实起见写出来——我读代码时以为有 bug、实测发现是对的：

1. **`parseArtifactBlocks` 的块边界计算**：`blockEnd = endMatch ? open.end + endMatch.index + endMatch[0].length : nextOpen`
   看起来在"有 END"时多加了 `open.end`，像会漏掉/吞掉字符。**实测是对的**：
   有 END 时 `min(blockEnd, nextOpen) === blockEnd`，且 `blockEnd` 恰好等于"块结束标记之后"的位置；
   两块的正文长度与期望完全一致（我构造了 118 字 × 2 块的用例逐字核对）。
   **不要"修"它。**
2. **`coerceInPlace` 的返回值在递归里被丢弃**（第 220-221 行只在 `!== NO_MATCH` 时赋回）：
   看起来"嵌套对象被删字段时，`changed` 传播了但替换值丢了"。**实测没问题**——对象分支是**就地修改**
   （`delete value[key]`、`value[key] = fixed`），返回值只在整个值需要**被替换**（枚举收敛）时才用。
3. **`resolveChain` 对没有 provider 前缀的 token 一律猜 `deepseek-official`**：
   注释写着"含 `DeepSeek-` 前缀的优先给 aiping"，**代码里没有这个判断**（`providers.js:55-57`）。
   所以 `.env.example` 里那个 `HANDOFF_MODEL_CHAIN` 示例会把 `aiping/GLM-5.3` 正确解析，
   但如果有人写裸的 `GLM-5.3`，会被发给 DeepSeek 官方然后失败。
   **这是注释与实现不符，不是崩溃**，但注释描述的逻辑确实没实现。
