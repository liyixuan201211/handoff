## 我尝试攻击但**没成功**的方向（14 个）

**1. 交付物名字的 HTTP 响应头注入（CRLF 注入）**
构想：让 `artifact.name` 含 `\r\nX-Injected: yes`，看 `Content-Disposition` 会不会被拆成两个头。
失败原因：`sanitizeFilename()`（`src/routes/jobs.js:114-132`）先把 `[\u0000-\u001F\u007F]`
（含 CR/LF）替换成空格，再过 `[/\\:*?"<>|]`、`\.{2,}`、以及一个 Unicode 白名单，
最后 `contentDisposition()` 用 `encodeURIComponent` 走 RFC 5987。
实测头是 `attachment; filename="a b X-Injected yes.md"; filename*=UTF-8''a%20b%20X-Injected%20yes.md`
—— 注入串变成了文件名的一部分，**没有裸 CR/LF，没有第二个头**。这个方向是干净的。

**2. `templateId` 的路径穿越读任意文件**
构想：`{"templateId":"../../../etc/passwd"}` 让服务端读任意 JSON。
失败原因：`loadTemplate()`（`engine.js:120-132`）先过 `/^[a-z0-9][a-z0-9-]{0,40}$/i`，
再过 `path.resolve` 前缀断言，最后必须 `JSON.parse` 成功。
实测 11 种穿越形态全部静默降级成 `templateId: null`，没有任何文件被读。

**3. `artifactId` / `jobId` 的路径穿越读文件系统**
构想：`/api/jobs/job_x/artifacts/..%2F..%2F..%2Fetc%2Fpasswd/download`。
失败原因：`JOB_ID_RE = /^job_[a-z0-9]{8,32}$/` + `path.resolve` 前缀断言（json-store 双保险），
路由层还会在 artifact 列表里 `find`，不命中就 404。实测 8 种形态全部 404，
响应体里没有 `/etc`、没有 `root:`。

**4. 静态目录穿越读源码**
构想：`GET /../src/server.js`、`/%2e%2e/%2e%2e/src/server.js`、`/..%2F..%2Fsrc%2Fserver.js`。
失败原因：Express 的 `express.static` 自己做了 realpath 校验，
未命中的路径被 SPA 兜底 `app.get('/{*splat}')` 接住，返回 index.html。
实测四种形态全部 200 + HTML（**不是**源码）。

**5. 100MB 请求体把服务打崩**
构想：`Content-Length: 104857600` 的 JSON。
失败原因：`express.json({ limit: '256kb' })` + 专门的 `entity.too.large` 处理，
实测 `413 {"error":{"code":"PAYLOAD_TOO_LARGE","message":"内容太大了，请精简一下再试。"}}`。

**6. `Content-Type: text/plain` 带 JSON body 绕过解析**
构想：让 express 不解析 body，把 `req.body` 变成 `{}` 或 undefined 骗过校验。
失败原因：express.json 只处理匹配的 content-type，其它情况 `req.body` 为 undefined，
`requireGoal(undefined)` 直接 400。实测两种形态都是 400，没有 500，也没有静默建任务。

**7. 并发写同一个任务文件造成 `fs.rename` 互相覆盖**
构想：20 个 job × 30 次并发 `updateJob`，同时外部狂读，期望看到半截 JSON 或计数丢失。
失败原因：`atomicWrite`（写 `.tmp` → `fsync` → `rename`）+ `withLock`（per-id promise 链）。
实测 **221,840 次读取，0 次解析错误、0 次 ENOENT、0 个残留 `.tmp`，计数全部精确为 30**。
这个实现比大多数"用数据库"的方案还稳。

**8. SSE 立刻断开 100 次造成监听器/定时器泄漏**
构想：100 个连接建立后立即 abort，反复 4 轮，看 `events.listenerCount(id)`。
失败原因：`sseHandler` 的 `cleanup()` 是幂等的，且 `req/res` 上挂了 4 个事件。
实测 4 轮 × 100 次之后 listenerCount 仍然是 **0**，活跃 handle 数不变。

**9. `Last-Event-ID` 传负数 / 超大数 / 非数字 / 科学计数法把服务打崩或造成 OOM**
构想：`Last-Event-ID: 99999999999999999999`、`-5`、`abc`、`9e99`。
失败原因：`resolveSince()` 用 `Number.parseInt` + `Number.isFinite(n) && n >= 0` 过滤。
实测最坏情况是"多发 500 帧"或"少发 0 帧"，**没有崩溃、没有 OOM**。
（"少发 0 帧"就是 S9-5 那条静默失败，但它是逻辑问题，不是可用性问题。）

**10. 前端 XSS：`</script><script>alert(1)</script>`**
构想：交付物正文里放裸 script、`<img onerror>`、`<iframe src=javascript:>`、事件属性。
失败原因：`renderMarkdown` 先 `stripControlChars` → 抽代码块（用原文、再 escape）→
其余每段 `escapeHtml` 之后再插标签。
实测 DOM 里 `script` 只有 `/app.js` 一个，`on*` 属性 **0 个**，
`window.__XSS_FIRED` 始终为 `null`，没有弹窗。这是全项目质量最高的一块。

**11. markdown 链接协议的 3 种绕过（大小写 / HTML 实体 / 控制字符）**
构想：`[x](jAvAsCrIpT:alert(1))`、`[x](java&#115;cript:alert(1))`、`[x](java\tscript:alert(1))`。
失败原因：`safeHref()` 先去 `[\u0000-\u0020\u007f]` 再 `toLowerCase()` 判定，
而 `inline()` 在判链接之前先 `unescapeBasic()` 把 HTML 实体还原成字符。
实测 8 种 payload 全部降级成纯文本，`href` 里 0 个危险协议。

**12. 全流程有外部请求（违背"零外部依赖"承诺）**
构想：用 `performance.getEntriesByType('resource')` 抓全量资源。
失败原因：`index.html` 没有任何 CDN，前端全是本地 ES module，无字体无图标库。
实测打开首页 + 历史 + 任务详情：**EXTERNAL: []**（0 个非本机请求）。

**13. 375px 手机尺寸横向滚动 / 按钮点不到**
构想：`scrollWidth > clientWidth`、点击目标小于 32px。
失败原因：设计系统用了流式布局 + `clamp()`。
实测四个页面 `overflow` 全部为 0，没有小于 32×32 的按钮，
textarea 字号 16.32px（≥16px，iOS 不会强制放大）。

**14. 只用键盘走不完「新建任务 → 看结果」**
构想：Tab 顺序断裂、焦点环不可见、提交后焦点丢失导致后续 Tab 到不了结果区。
失败原因：skip-link + 语义化标签 + 完整的 `:focus-visible` 样式。
实测 Tab 顺序完整（textarea → audience → tone → 演示按钮 → 提交），
焦点环 2.5px 实心可见，按 Enter 提交后任务进入详情页，
继续 Tab 能找到「复制」按钮。
**唯一的小瑕疵**：提交后 `document.activeElement` 变成 `BODY`（焦点没有移到新页面），
读屏用户会"失去位置"。我没有把它单列为缺陷（产品有 `aria-live="polite"` 在播报），
但建议在 `render()` 后把焦点移到 `<h1>` 或新页面容器上。

## 顺带发现：那条基线里的 flake，机制我找到了

`tests/e2e/pipeline.test.js:58`「引擎确实把任务写到了磁盘」偶发红：

```
AssertionError: expected 'running' to be 'done'
 ❯ tests/e2e/pipeline.test.js:74:27
```

它不是测试写得不好，而是**产品行为的直接后果**：

1. 测试先 `waitForJob(app, id)`（轮询 `GET /api/jobs/:id`）→ 看到内存里已经是 `done`；
2. 然后等文件**出现**（`while (!existsSync) sleep(50)`）；
3. 文件一出现就读 —— 但此刻磁盘上那份可能是**更早一次 save 写的 `running`**。

因为 `saveJob()` 在每次写盘时都会 `job.updatedAt = Date.now()` 并**直接序列化那个活对象**，
而流水线在终态保存之后还会有别的写（`startJob` 里的 `running.set`、`routes/jobs.js:253`
的兜底持久化、`withLock` 队列尾部的后续写）。多个写在同一个 id 上排队，
最后落到盘上的不一定是"最新的那个状态"。

**对用户的影响**：`GET /api/jobs/:id` 读的是内存活对象，所以单进程下界面是对的；
但如果用户在**看到"已完成"之后立刻强杀进程/关机**，重启后磁盘上那份可能是 `running`，
被 `markInterruptedJobs()` 标成"被中断，可以重试" —— 而他明明已经拿到交付物了。
这条我按"低"记录，与 S9-8 合并考虑即可（修 S9-8 时顺手把"终态先落盘再对外可见"做了）。

复现（我跑了两遍，第二遍复现）：

```

 × 引擎确实把任务写到了磁盘（刷新页面 / 重启进程之后还在）
   AssertionError: expected 'running' to be 'done'
```

## 附二：全仓测试里的另一处 flake —— 它其实是 S9-2 的同一个根因

```
$ npx vitest run
 FAIL  tests/e2e/pipeline.test.js > C. 失败与边界 > 回归（缺陷 #5 已修复）：前端发 { message } 与契约的 { text } 都必须能用
 AssertionError: expected 409 to be 200
 ❯ tests/e2e/pipeline.test.js:566:54
 Test Files  1 failed | 11 passed (12)
      Tests  1 failed | 363 passed | 12 expected fail | 1 skipped (377)
```

这条用例在 `await waitForJob(app, id)` 之后立刻发 message，期望 200；实际拿到 409。

**机制**：`waitForJob` 只轮询 `GET /api/jobs/:id` 看状态变成终态，
但**终态是在内存对象上先改的**，流水线随后还要跑收尾（安全审计 → `gradeDelivery` → `save`）。
在"状态已经是 done、`running` map 还没删"的这个窗口里发 message，
就会撞上 `running.has(jobId)` 的 409。用例 566 行没有等这个窗口关闭。

这不是"测试写错了"，而是 S9-2/S9-4 的同一个根因（`running` 的生命周期与状态机不同步）
在测试里的又一个受害者。**建议修法**：用例在发消息前等 `engine.__internals.running` 里
没有这个 id，或者（更好）由产品侧保证"终态对外可见时，流水线一定已经收尾"。
