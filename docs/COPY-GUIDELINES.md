# 交接 Handoff 文案规范（COPY-GUIDELINES）

给**以后要改这个产品文案的人**看的。改任何一句用户能看到的字之前，先读这一页。

产品面向的是护士、小店主、老师、学生、退休的人。**他们判断这个产品好不好，不看功能，看它怎么说话。**

---

## 〇、先认人

改任何一句话之前，先问自己：这句话是写给下面哪一位的？她/他看完会不会更安心一点？

| 谁 | 情况 | 她最在意什么 | 她最怕什么 |
|---|---|---|---|
| **李姐** 48 岁 | 社区医院护士长，用手机办事 | 别让我写长句子，别让我等 | 被反问一堆问题 |
| **老王** 55 岁 | 开小超市，会用微信 | 能不能办成事 | 出问题时觉得「是我点错了」 |
| **小陈** 29 岁 | 毕业三年，懂一点技术 | 别把我当傻子 | 看到客服腔和「一眼假」的话 |
| **张姨** 66 岁 | 退休教师，眼睛不好 | 别让我点错，别让我弄坏东西 | 觉得自己操作失误了 |

**一句话验收标准**：如果李姐看到这句话，她会觉得对面是个靠谱的人，还是一个机器？

## 一、我们说话的 5 条原则

### 原则 1：说「你」和「我」，不说「用户」和「本系统」

产品里所有虚拟员工都是「人」，所以文案里的人称也必须是人对人的。

- ❌ 反例：`输入内容不合法。`（`src/pipeline/engine.js:193`）
  → 用户会想：我犯法了？
- ✅ 正例：`这段话里有我们处理不了的内容。换个说法再试一次。`
- ❌ 反例：`action: '已拒绝处理，等待用户补充内容'`（`src/security/guard.js:217`，会显示成「我们做了：…」）
  → 「用户」就是正在看屏幕的那个人，用第三人称说他自己，很奇怪。
- ✅ 正例：`没有开始处理，等你说一句话`

### 原则 2：能用生活动词，就不用名词；能说「办事」，就不说「流程」

名词化是官腔的源头。「进行验证」「对内容进行处理」「做出判断」都是同一个毛病。

- ❌ 反例：`模型输出的结构不符合要求：$.confidence 取值必须是 high/medium/low 之一，实际是 0.95`（`src/llm/gateway.js:341`）
- ✅ 正例：`AI 这次答得不对路，我们已经让它重做一遍。`
- ❌ 反例：`'已自动修正模型输出中的个别格式偏差（例如把 0.95 归一为 high）。'`（`src/llm/gateway.js:335`）
- ✅ 正例：`它有几个地方写得不太规范，我已经顺手改好了。`
- ❌ 反例：`'验收完成：5/6 项通过 → pass_with_notes'`（`src/pipeline/stages.js:381`）
- ✅ 正例：`验收完了：6 项里过了 5 项。能用，有几点提醒。`

### 原则 3：出错时，先说「不是你弄坏的」，再说「怎么办」

用户出错时的第一反应不是「怎么办」，而是「是不是我搞错了」。必须先把这一句接住。

失败消息固定四段式：

> **① 发生了什么（不用技术词）→ ② 是我的问题吗（主动担责）→ ③ 东西还在不在（保住已有成果）→ ④ 我现在做什么（一个明确动作）**

- ❌ 反例：`'任务失败，且未能保存失败原因。'`（`src/pipeline/engine.js:333`）
- ✅ 正例：`这次没做成，连原因都没记下来。点重试再走一遍。`
- ❌ 反例：`'交付没达标：没有产出任何可用的内容'`（`src/pipeline/engine.js:629`）
- ✅ 正例：`这次没做出能用的东西。已经做过的工作都留着，点重试可以再做一遍。`
- ✅ 范本（**请保留，并照这个写**）：`src/server.js:310` —— 「这次运行被中断了（服务被关闭或电脑休眠）。已经做好的部分都保留在上面，点「重试」可以接着做完。」

### 原则 4：等待时给量级，成功时给出口

「处理中」「请稍候」是最没有信息量的两句话。用户要知道的是**多久**和**我能不能走开**。

- ❌ 反例：`'正在让团队接着做，稍等…'`（`public/app.js:1306`）
- ✅ 正例：`正在接着做，一般要 1～3 分钟。你可以先去做别的，做完这里会变。`
- ❌ 反例：`'任务完成了。上面的交付物可以直接复制或下载拿走。'`（`public/app.js:1297`）—— 事实正确，但冷。
- ✅ 正例：`都弄好了。上面的成果可以直接复制或下载拿走；有哪块不对，在下面说一句，我们重做。`
  成功消息要带一个**补救出口**：用户拿到东西后的第一反应是「这能用吗」，要给他一个说「不对」的地方。

### 原则 5：不确定就说不确定，不要装

这个产品最值钱的语气是诚实。写「我不太确定」比写「请注意核实」有用一百倍。

- ✅ 现成范本（`public/app.js:1047`）：`我们比较有把握` / `把握一般` / `不太有把握，建议你核一下`
- ✅ 现成范本（`src/pipeline/stages.js:337`）：`'审查员这次没挑出问题（可能是内容确实扎实，也可能是它偷懒了）。'`
  —— 愿意承认自己可能偷懒，这是信任的来源。**不要为了「显得专业」把它改掉。**
- ❌ 反例：`本模板不提供医疗诊断，仅帮助理解报告与准备问诊问题。`（`templates/health-prep.json`）
- ✅ 正例：`这不是看病，不能代替医生诊断。它帮你听懂报告、想好该问医生什么。`

## 二、术语表（唯一正确写法）

**改文案时，右列是唯一允许出现的写法。** 左列出现即为缺陷。

| 不要写 | 要写 | 备注 |
|---|---|---|
| 交付物 / 产物 | **成果** | 界面上一律「成果」，不要两种并存 |
| 提示词 | **怎么跟 AI 说话** | 用户没有这个概念 |
| 模型 / 大模型 | **AI** | 需要解释隐私时可用「AI 服务」 |
| 服务端 / 本机服务 | **这个程序** / 用浏览器 / 自带的 | 用户在「本机」和「网上」之间区分 |
| 接口 | **地址** | |
| 队列 / 排队中 | **等着开工** | |
| 流水线 | **步骤** / 一步一步来 | |
| 阶段 | **步骤**；讲人时用 **这一位** | |
| 日志 | **记录** | 「看得见团队在做什么」是卖点，用「记录」才接得上 |
| 失败 | **没做成** | 状态标签专用 |
| 需要返工 | **有几处得改，先别急着用** | |
| 生成（「没有生成交付物」） | **做出来** | |
| 渲染 / 拉取 / 输出 / 响应 | **显示 / 取回来 / 写出来 / 回话** | |
| 请求（「请求内容不是合法 JSON」） | **发过来的内容** | |
| 字段 / 取值 / 参数 | **（不显示给用户）** | 只进日志 |
| 校验 / 验收结果 | **把关 / 质检** | |
| API Key | **密钥**（尽量配「密码」一起说） | 面向用户时不用英文 |
| 截断 | **只看了前面…** / **写到一半断了** | |
| 打码 | **打上马赛克** | |
| 任务 / 活儿 | **任务**（名词）；「干活」只作动词搭配 | |
| 密钥（对李姐） | **你填的账号和资料** | 隐私说明处优先用这个 |
| CDN | **外面的网站** | |
| JSON / finish_reason / pass_with_notes / research / intake | **（一律不显示）** | 任何英文标识符与状态码都不许出现在用户可见区域 |

**虚拟员工名册（不要改）**：接待员、项目经理、调研员、执行专员、审查员、质检员、交付专员。这个命名是整个产品最好的语言资产——**用户看到「质检员」三个字，就知道有人在替他把关**。

> ⚠️ 注意：`src/prompts/index.js:27-34` 里每个员工都写了 `desc`（如「专门找自己的毛病」），但**目前没有任何界面引用它**。首页正在用一段 95 字的长句临时解释同样的信息（`public/app.js:287`）。下次做界面时可以把这个浪费捡起来。

## 三、错误消息的三种模板

### 模板 A：好消息（完成了什么）

```
[做了什么事] + [你现在可以做什么] + [不满意怎么办]
```

- 例：`都弄好了。上面的成果可以直接复制或下载拿走；有哪块不对，在下面说一句，我们重做。`
- 例：`验收完了：6 项里过了 5 项。能用，有几点提醒。`
- 禁用：「操作成功」「已为您生成以下内容」「任务已完成」。

### 模板 B：坏消息（没做成，但东西还在）

```
[哪里没做成] + [不是你弄坏的] + [已经做好的还在] + [点哪个按钮能接着做]
```

- 例（可作模板）：`这一步没做成，原因没记下来。前面做好的都留着，点重试可以接着做。`
- 例（可作模板）：`这次没做出能用的东西。已经做过的工作都留着，点重试可以再做一遍。`
- 禁用：「任务失败」「交付没达标」「没有实际价值」「发生错误」。

### 模板 C：需要用户行动（缺信息 / 内容不合规 / 主动问他）

```
[为什么现在停下来] + [我需要你说的那一句话，给个例子] + [说完之后会怎样]
```

- 例：`还没写要办什么事。用一句话说就行，比如「帮我看下这份租房合同」。`
- 例：`太长了（4231 字），最多收 4000 字。先留最要紧的，剩下的分两次发。`
  → 注意：超长消息必须给出**取舍办法**，不能只说「请精简」。
- 例：`还没配置好 AI 服务。请帮你装这个程序的人填一下密钥，填好重启就行。`
  → 注意：当用户无法自己解决时，**明确告诉他找谁**（「帮你装这个程序的人」），而不是给他一个他读不懂的路径。
- 禁用：「请补充必要信息以继续」「输入内容不合法」「请求参数错误」。

### 三种模板共用的硬规则

1. **每条错误消息最多一个动作。** 出现两个以上按钮的指引，用户就不知道该点哪个。
2. **不许出现英文、下划线、`$`、`.` 开头的路径、`.env`、状态码枚举。**
   - 允许保留的唯一数字是三位 HTTP 状态码（如「编号 429」），因为它能和客服对上。
3. **技术细节只进服务端日志**（`console.error` / `job.error` 的日志侧），不进用户可见区域。
4. **不许把责任推给用户。** 无论如何不能出现「你操作错误」「请检查你的输入」。
5. **改错误消息时，必须同时改 `public/api.js` 的 `friendlyError` 表。** 表里的 key 必须和 `src/llm/errors.js` 的 `ERR` 完全一致——目前这张表有 3 个 key 根本不存在，等于死文案（详见 `docs/reports/S13-语言质量.md` 的 P0-5）。

## 四、禁止出现的词与句式清单

### 4.1 禁止词（见到就换）

| 禁止 | 换成 |
|---|---|
| 提示词、大模型、模型 | 怎么跟 AI 说话 / AI |
| token、API Key、Bearer、密钥（面向用户时） | 密钥 / 密码 / 你填的账号 |
| 降级、兜底、队列、并发、实例、超时（作技术词） | （不显示）／ 换了一条线路 / 等着开工 / 没回应 |
| 阶段、流程、流水线、编排 | 步骤 / 一步一步来 |
| 交付物、产物、交付 | 成果 / 做出来的东西 |
| 结构化、校验、渲染、解析、序列化、截断 | （不显示）／ 答得不对路 / 显示 / 读到 / 只看了前面… |
| 请求、响应、参数、字段、接口、服务端、本机服务 | 发过来的内容 / 回话 / 地址 / 这个程序 |
| 生成、创建、执行、操作、处理 | 做出来 / 建起来 / 干活 / 点一下 / 办 |
| 失败、错误、异常、不合法、无效 | 没做成 / 出了点问题 / 有处理不了的内容 |
| 返工、达标、质量不达标、没有价值 | 有几处得改 / 能用 / 还不能用 |
| 成功、已完成（作提示语时） | 都弄好了 / 好了 |
| 请稍候、处理中、加载中（单独出现时） | 正在…，一般要 X 分钟 |

### 4.2 禁止句式

| 禁止句式 | 为什么 | 换成 |
|---|---|---|
| 「请……以继续」/「请……后重试」 | 官腔，且没有说清做什么 | 直接说动作：`点重试就好。` |
| 「已为您……」 | 客服腔，「为您」是错的敬语 | `我已经……了。` 或直接删掉 |
| 「操作成功」 | 没有人这么说话 | `好了。` / `改好了。` |
| 「发生错误」「出现异常」 | 没说什么事，也没说怎么办 | `这一步没做成。`＋下一步 |
| 「对……进行处理」「进行……操作」 | 名词化堆叠 | 直接用动词：`删掉` / `看一下` |
| 被动句（「任务已被取消」「内容已被拦截」） | 不知道是谁做的 | `已经停了。` / `为安全起见停下了。` |
| 「建议您……」「请注意……」 | 正确的废话，等于没写 | 给出具体动作，或整句删掉 |
| 「具体情况具体分析」「视情况而定」 | 我们没有提供任何信息 | 给出判断条件 |
| 括号里塞技术注释（`（finish_reason=length）`） | 把内部状态码贴到界面上 | 只进日志 |
| 同一屏出现两种叫法 | 用户会以为是两种东西 | 回到第二节术语表 |

### 4.3 长度与结构

- 界面上**任何一段话不超过 60 字**。首屏第一段不超过 40 字。
- 超过 60 字就拆：第一句立结论，后面才是解释。
  - 反例：`public/app.js:287` 的 95 字首屏段落。
  - 正例：`你只管用大白话说想要什么，剩下的交给看得见的团队。`
- 一段里**不出现两个以上的数字**。用户记不住。
- 用「，」和「。」，不用「；」串联三个以上分句。

## 五、改文案的流程（照做就不会出事）

1. **先认人**：这句话是给李姐、老王、小陈还是张姨看的？
2. **查术语表**（第二节）：有没有禁止词？叫法和其他地方一致吗？
3. **定模板**（第三节）：这是好消息、坏消息，还是要用户行动？套对应模板。
4. **过一遍禁词表**（第四节）：逐条对照。
5. **念出来**：把改后的句子读一遍。**如果这句话你不会对邻居说出来，就重写。**
6. **同步改测试**：以下位置有断言，改文案必须一起改，否则会被误判为「引入回归」——
   - `tests/unit/frontend.test.js:328-332`（`排队中` / `进行中` / `失败` 三个状态标签）
   - `tests/unit/frontend.test.js:445`（`friendlyError` 行为）
7. **同一场景多处出现的，一起改**。已知的重复点：
   - 「找不到这个任务」在 6 处、且有两种写法（`src/routes/jobs.js:259` `264`、`src/routes/stream.js:19` `24` 写「找不到这个任务」；`src/pipeline/engine.js:1018` `1095` 写「没找到这个任务」）
   - 断线提示在两处（`public/app.js:556-561` 与 `public/ui.js:666-671`）
   - 「请说一下你需要什么帮助」与「请先告诉我们要办什么事」是同一个错误的两套说法

**建议补一条长期护栏单测**：用户可见的任何错误消息里，不允许出现连续 4 个以上英文字母，也不允许出现 `$` 或以 `.` 开头的路径。这一条能一次性防住「`$.confidence`」「`NETWORK_ERROR`」「`请求内容不是合法的 JSON`」整类问题。

## 六、一句话总结

> **用户看不懂的词，就是我们要删的词。
> 用户不知道自己该做什么的句子，就是没写完的句子。
> 用户看完觉得自己做错了的句子，就是必须重写的句子。**
