# 交接 Handoff —— 性能画像与已知瓶颈

> 读者：改这个仓库的人。
> 目的：**在你动手之前，知道哪些数字是被测过的、哪些地方一改就会变慢、改完必须复跑什么。**
> 复跑命令：`node scripts/bench.js`（全部，约 100 秒）；单跑见 §6。
> 最近一次全量实测：见 `docs/reports/S10-性能与可靠性.md`（含被测源码的 git rev 与文件哈希）。

## 0. 一句话画像

**这是一台给一个人用的本地小服务，它在正常路径上非常快，问题几乎全部集中在「持久化」这一层。**

| 维度 | 实测 | 判定 |
|---|---|---|
| 页面级端点（列表 / 详情 / 下载） | p95 **5 ms 以内** | ✅ 远低于「超过 1 秒就觉得卡」的红线 |
| 打开一个含 3×3000 字交付物的任务 | p95 **4~8 ms**，响应 30 KB | ✅ |
| 100 个任务同时存在 | 列表与详情延迟无明显变化 | ✅ |
| 50 条 SSE 连接（同一个 job） | 全部建立 55 ms，事件广播 8 ms | ✅ |
| 200 轮「建→跑→看→连 SSE→删」 | 堆内存 **回落**，监听器 / 写队列 / running 表全为 0 | ✅ 无泄漏 |
| 不删任务时的常驻内存 | 事件日志 37.5 KB/任务；200 个大任务常驻 **+66 MB** | ⚠️ 只增不减 |
| 磁盘：一个 8 阶段任务 | **26 次全量写盘**，写入 482 KB（写放大 13.6×） | ⚠️ |
| 每 30 秒的后台同步 | 2000 个任务时 **359 ms** 重读整个目录 | ⚠️ |
| 持久化竞态 | `sweepTmpFiles()` 会删掉正在写的 `.tmp` → 任务直接失败 | 🔴 **必修** |
| 崩溃恢复 | `kill -9` 后重启 → `failed` + `INTERRUPTED` + 可重试 | ✅ |

**结论一句话：延迟不是问题，磁盘写入和内存常驻是问题；其中 `sweepTmpFiles()` 的竞态是唯一一个会让用户任务直接失败的缺陷。**

## 1. 硬红线（改代码前请先认同这些数）

给普通人的产品，「快」的定义不是 QPS，而是这三条：

1. **点击到看见 ≤ 1 秒。** 本仓库的余量是 100 倍以上，任何改动都不该把它吃掉。
2. **内存不随时间增长。** 用户可以接受启动就占 60 MB，不能接受「越用越大」——那意味着他得重启电脑。
3. **不出现「永远转圈」和「莫名失败」。** 这两件事比慢 10 倍更伤信任。

`scripts/bench.js` 里的判定阈值就是按这三条定的：

| 指标 | ✅ | ⚠️ | 🔴 |
|---|---|---|---|
| 端点 p95 | < 300 ms | 300 ms ~ 1 s | > 1 s |
| 冷启动（含加载全部任务） | < 1 s | 1~3 s | > 3 s |
| 堆增长 / 200 轮 | < 16 MB | 16~48 MB | > 48 MB |
| 保存失败 / 崩溃后卡死 | 0 | — | > 0 |

## 2. 已知瓶颈（按影响排序）

### 🔴 2.1 原子写的临时文件会被后台清扫删掉，导致任务失败

- **现象**：新建任务时直接 500；日志里是
  `ENOENT: no such file or directory, rename '.../job_xxx.json.tmp' -> '.../job_xxx.json'`。
  把同步周期缩短复现时，50 个任务里 14~18 个因此失败。
- **根因**：`sweepTmpFiles()`（`src/store/json-store.js:123-142`）**无条件**删掉目录里所有
  `*.json.tmp`；而它被 `loadFromDisk()`（同文件 `:230`）在每次重载末尾调用，
  `startSyncTimer()`（`:251-261`）每 30 秒就会 force 重载一次。
  另一边 `atomicWrite()`（`:109-120`）用固定的 `${file}.tmp` 名字，且中间有一次 `fsync`（实测 5~8 ms），
  这段时间里临时文件是「活的」。
- **对用户的感受**：他点了「开始」，弹出一个他看不懂的错误；或者任务跑到第 3 个阶段突然失败。
  概率上大约每 200 个任务命中一次（估算法见报告），**但只要命中一次，用户就会认为这软件不靠谱**。
- **修复建议**（按推荐顺序）：
  1. 临时文件名唯一化：`${file}.${process.pid}.${counter++}.tmp`，这样清扫器永远碰不到别人的文件（最小改动，彻底解决）。
  2. 清扫只处理「陈旧」文件：`stat.mtimeMs < Date.now() - 5 * 60_000` 才删。
  3. `sweepTmpFiles()` 只在进程启动时（`startServer` 里 `loadFromDisk()` 之后）跑一次，不要挂在周期重载上。
- **改完复跑**：`node scripts/bench.js disk`（看 §3b 的两行必须变成「不会 / 0/50」）。

### ⚠️ 2.2 内存里常驻「200 个完整任务（含交付物正文）」

- **现象**：200 个 178 KB 的任务常驻 **+66 MB**；换成 500 KB 的任务，上限约 **185 MB**。
  删除全部任务后回落到 15.7 MB —— 说明不是碎片，就是这些对象。
- **根因**：`MAX_MEMORY_JOBS = 200`（`src/store/json-store.js:20`）+ `cachePut()`（`:153-161`）缓存**整个 job 对象**，
  而 `job.artifacts[].content` 就是交付物全文。
- **对用户的感受**：跑了一两个月、攒了几百个任务之后，这个「小工具」常驻几百 MB，
  在 8 GB 的老电脑上就是「它把内存吃光了」。
- **修复建议**：
  1. 缓存里**剥掉 `artifacts[].content`**，详情接口按需从磁盘读一次（详情页 p95 目前只有 2 ms，读盘完全放得下）。
  2. 或者按「字节预算」而不是「个数」淘汰（例如最多 32 MB，超出按 `updatedAt` 丢）。
- **改完复跑**：`node scripts/bench.js memory`（看「200 个 N KB 级任务常驻内存」与「释放检验」两行）。

### ⚠️ 2.3 每个任务的事件日志永不回收（只按 500 条封顶）

- **现象**：保留 200 个任务 → 事件日志常驻 18.9 MB（序列化）/ 堆 37.5 KB 每条任务；
  保留 500 个 → 单调上升，没有任何回落机制。只有 `DELETE /api/jobs/:id` 会调 `events.drop()`。
- **根因**：`JobEvents.#logs`（`src/store/events.js:14` / `publish()` `:29-40`）每个 `jobId` 一个条目，
  只裁剪**单个 job 内的 500 条**（`MAX_LOG_PER_JOB`，`:13`），**从不清理「job 本身」这个 key**。
- **对用户的感受**：一夜之间涨几 MB（实测 60 个任务 ≈ 2.2 MB），单看不吓人；
  但它是**只增不减**的，且普通用户永远不会去点删除。
- **修复建议**：在 `publish()` 里顺手淘汰 `#logs` 中最久未更新的条目（保留最近 N=200 个 job 的日志），
  或给 `#logs` 加一个按 job 数/字节数的上限，配一个惰性 LRU。
- **改完复跑**：`node scripts/bench.js memory`（看「事件日志的真实堆成本 / 任务（200→500 段斜率）」）。
  注意：**不要**用「200 轮删除」那一组来验证，那一组本来就是干净的。

### ⚠️ 2.4 每个阶段边界都全量重写整个 job 文件

- **现象**：一个 8 阶段任务 **26 次** `saveJob`，累计写入 482.1 KB，而最终文件只有 35.5 KB —— **写放大 13.6×**。
  402 KB 的大任务单次写盘 p50 8.3 ms，整任务理论写入量 ≈ 10.2 MB。
- **根因**：`saveJob()`（`:281-300`）与 `updateJob()`（`:338-356`）都是「序列化整个 job → 写临时文件 → `fsync` → rename」，
  而引擎在每个阶段开始/结束、产物落地、验收、交付各调一次（`src/pipeline/engine.js` 里 `await save(job)` 共 20+ 处）。
- **对用户的感受**：一个任务里多出 100~200 ms 的磁盘等待 + 10 MB 写盘。对「几分钟才跑完的任务」几乎无感，
  但在机械硬盘/网络盘上会明显拖慢，而且**每次 `fsync` 都是一次 SSD 写入**。
- **修复建议**：
  1. 阶段开始/结束这种「只改状态」的写入不必落全量正文 —— 把 `stages`/`usage` 与 `artifacts` 拆成两个文件。
  2. 或者给写盘做 200~500 ms 的合并（写请求排队 + 去抖），阶段事件仍然即时 `emit`。
  3. `fsync` 可以只在「任务终态」这一次做；中间态掉电重来即可（现有 `INTERRUPTED` 恢复已经能处理）。
- **改完复跑**：`node scripts/bench.js disk`。

### ⚠️ 2.5 每 30 秒把整个任务目录重读一遍

- **现象**：2000 个任务（小型 2 KB）→ **278 ms**；2000 个含 3×3000 字交付物的任务（82 MB）→ **359 ms**。
  （冷启动加载同一批数据分别是 290 ms / 384 ms。）
  这个成本每 30 秒发生一次，而且和用户操作无关。
- **根因**：`startSyncTimer()`（`:251-261`）定时 `loadFromDisk({ force: true })`，而 `loadFromDisk()`（`:188-240`）
  是「`readdir` + 逐个 `readFile` + 逐个 `JSON.parse`」，**全部任务都要读**，之后才按 200 上限淘汰。
- **对用户的感受**：任务攒多之后，每半分钟有一次明显的磁盘活动；慢盘上会造成「点了没反应」的偶发卡顿。
  更糟的是它**顺带触发了 2.1 的清扫竞态**。
- **修复建议**：
  1. 同步只做「`readdir` + 比对 `mtime`/大小」，只重读变化过的文件（现在等于每次全量重建）。
  2. 或者把周期从 30 s 放宽到 5 min，并在 `GET /api/jobs` 时按需刷新。
  3. 无论如何，**不要**在周期重载里跑 `sweepTmpFiles()`。
- **改完复跑**：`node scripts/bench.js startup`。

### ⚠️ 2.6 `/api/health` 每次请求同步打开 5 次 sqlite

- **现象**：`inspectChain()` 单次 **4.33 ms**，显式给 key 时 **0.00 ms** —— 差额全在磁盘上。
  `/api/health` 的 p50 因此是 6.2 ms，是其它端点的 3 倍。
- **根因**：`inspectChain()`（`src/llm/providers.js:139-152`）对降级链里 5 个 provider 逐个调 `resolveKey()`，
  本机没配环境变量时会落到 `keyFromCherryStudio()`（`:74-105`），用 `node:sqlite` 的 **`DatabaseSync`（同步 API）**
  打开 12.8 MB 的 Cherry Studio 配置库再关掉。
- **对用户的感受**：健康检查本身不慢，但它是**同步阻塞事件循环**的：这 4 ms 里服务对任何请求都不响应。
  如果用户的 Cherry Studio 库更大、或在被别的进程写（SQLite 会等锁），这里会变成几十毫秒到秒级。
- **修复建议**：把「密钥是否存在」按 provider 缓存（TTL 30~60 s），或改用异步读取；
  `/api/health` 不该是唯一能反映这件事的地方。
- **改完复跑**：`node scripts/bench.js latency`（看 `/api/health` 那一行与「同步 sqlite 的代价」）。

### ⚠️ 2.7 单机限流把「一分钟开 11 个任务」判为滥用

- **现象**：连续 `POST /api/jobs`，第 11 次开始返回 **429**（`操作太快了，请稍等一分钟再试`）。
- **根因**：`RATE_RULES`（`src/server.js:94-103`）沿用契约 §5.7 的「每 IP 每分钟 10 次」。
  在「单机、只有一个人、IP 全是 127.0.0.1」的场景下，这条规则挡住的**只有你自己**。
- **对用户的感受**：批量提交任务（或前端重试逻辑触发）时突然被拒，文案还说「请稍等一分钟」——
  他会认为「这软件限制我」。
- **修复建议**：对 loopback 地址放宽（或改成基于并发任务数而不是请求数），
  保留限流是为了「防脚本」，不是「防用户自己」。
- **改完复跑**：`node scripts/bench.js memory`（看「单机单用户连续建任务的限流阈值」）。

### ℹ️ 2.8 小事项（不急，但顺手可以改）

- `/api/templates` 每次请求都 `readdir` + 读 8 个文件 + `JSON.parse`（p50 2.5 ms）。
  模板是只读的，进程内缓存一次即可（`src/server.js:113-133`）。
- `listJobs()` 每次全量排序（`:163-165` / `:313-317`），50 个任务时无感；
  缓存口径改成字节预算后要留意这里。

## 3. 已经测过、**不是**问题的部分（不要为它们做优化）

写在这里，是为了避免后来的人把时间花在已经证明健康的地方：

- **HTTP 端点快得离谱**：所有页面级端点 p95 < 8 ms，含 30 KB 交付物的详情也一样。
  任务数从 1 涨到 50 对列表页没有可见影响。
- **SSE 不泄漏**：50 条连接建了再断，`listenerCount` 回到 0；
  一条事件广播到 50 个客户端 8 ms。
- **事件总线本身是有界的**：单个 job 的日志被 `MAX_LOG_PER_JOB=500` 卡住，不会 OOM（问题在 §2.3 的「job 条目」层面）。
- **写队列不泄漏**：`withLock()` 的自清理（`json-store.js:97-100`）实测正确，`pendingLocks()` 归 0。
- **`engine.running` 不泄漏**：终态任务会被 `running.delete()` 移除，`AbortController` 不会攒。
- **`DELETE /api/jobs/:id` 是干净的**：确实调了 `events.drop()`，删完事件日志 0 字节。
- **崩溃恢复是好的**：`kill -9` 后重启，任务变 `failed` + `INTERRUPTED` + 一句人话 + 可重试，
  已完成的产物与阶段全部保留。

## 5. 怎么读基准输出

```
node scripts/bench.js
```

输出里每一行是「指标 / 实测值 / 判定 / 依据」，最后有一张总表。开头会打印**被测源码的 git rev 与文件哈希** ——
发结论给别人时把那一行一起贴上，否则「测的是哪个版本」说不清。

输出里出现的两类「非实测」数字，读的时候要区分：

- **`≈ / 推算`**：由实测斜率外推（例如「一晚涨多少 MB」），外推用的算式写在依据里。
- **`估算（非实测）`**：真实周期太长（30 秒）跑不出统计量，例如 §2.1 在真实周期下的发生率。

## 7. 这份基准**测不出**的东西（诚实边界）

1. **真实模型下的端到端耗时**。基准用剧本模型（`tests/helpers/e2e-harness.js`），
   真实 API 的延迟、超时、降级重试完全没测。那属于功能测试（`scripts/dry-run.js`），不是性能基准。
2. **多用户 / 多并发**。本产品定位是单机单人，`HANDOFF_HOST` 默认只监听 127.0.0.1；
   基准没有、也不打算测「10 个人同时用」。
3. **Windows / 机械硬盘 / 网络盘**。所有数字来自一台 macOS/APFS/SSD 的机器。
   `fsync` 在这三种环境下的代价差异很大（§2.4 的结论会变）。
4. **长时间真实运行（几天）**。基准用 200/500 个任务压缩时间，不外推「连续跑 7 天」——
   那条曲线受用户真实使用频率影响，只能给斜率，不能给结论。
5. **单个任务的真实交付物体积分布**。基准用的是 3×3000 字（42 KB）与 178 KB 两档；
   真实模型输出多长取决于提示词与模型，不是一个固定值。
6. **纯客户端的开销**（浏览器渲染长 markdown、SSE 重连抖动）。基准只打 HTTP/SSE 接口。

## 8. 基准脚本本身的约束

- `scripts/bench.js` **绝不碰真实 `data/`**：自己在 `os.tmpdir()` 建临时目录，结束删除，
  并且有 `assertSafeDataDir()` 硬拦截。
- 演示模式默认把阶段步进从 700 ms 调到 0 ms（否则 200 轮要跑 20 分钟）。
  这只影响进度条节奏，不改数据结构 —— 脚本里有一项「保真度校验」用实测证明两种节奏的产物完全一致
  （阶段数 / 产物数 / 产物字符数 / 事件字节）。
  需要真实节奏时加 `--real-timing`。
- 脚本会自己用 `--expose-gc` 重启一次，否则堆数字包含未回收垃圾。
- 测的是真实 HTTP/SSE（`createApp()` + `listen(0)`），不是 supertest —— 中间件、限流、序列化都在链路上。
